# Contributing to Nagi OS

Nagi OS is an independent operating system in active Developer Preview work.
Contributions should preserve the architecture and should leave acceptance
evidence clear enough for someone else to reproduce.

## Before changing code or documentation

Read the repository rules in [`AGENTS.md`](AGENTS.md), the relevant sections
of the [primary implementation specification](docs/Nagi_OS_0.1_Codex_Implementation_Spec.md),
the current [implementation status](docs/implementation_status.md), and the
workstream that owns the change. Inspect `git status` and the relevant diff
first so existing work is preserved.

Implement milestones in their specified order. Keep each milestone state as
`PASS`, `PARTIAL`, `BLOCKED`, or `NOT STARTED`; report a `PASS` only when its
acceptance criteria have fresh evidence. If an implementation is independent
of a blocked dependency, record the exact dependent acceptance that remains
blocked and continue the independent work.

## Architecture and security

- Nagi is not a Linux, Windows, or macOS runtime. Host tools may build and run
  QEMU, but guest behavior must execute inside Nagi.
- Keep files, network protocols, windows, audio, packages, and AI in user-space
  services. Do not add high-level kernel syscalls for those services.
- Preserve capability checks and least privilege. Do not use allow-all access,
  root-like owner bypasses, or strengthened transferred handles as shortcuts.
- Treat AI and browser content as untrusted. Generated output must pass
  deterministic validation, policy, permission, and executor boundaries before
  side effects; AI must not run arbitrary shell commands or elevate authority.
- Keep third-party code pinned. Put Nagi-specific changes in tracked patch or
  adapter boundaries instead of undocumented edits to fetched caches.
- English is canonical for identifiers, APIs, commands, and diagnostics.
  User-facing strings follow the shared rules in
  [`language-architecture.md`](docs/architecture/language-architecture.md);
  `en-US` and `ja-JP` are equal first-class Nagi 0.1 user languages.
- Treat IDL/specification sources as authoritative and regenerate bindings.
  Do not edit files marked generated by hand.

## Build and verification

Run commands from the repository root. `./nagi --help` shows the current
command surface; on Windows, use `.\nagi.ps1` with the same subcommands.

For a host-compatible change, start with the relevant focused Cargo check or
test, then use the repository commands as appropriate:

```sh
./nagi doctor
./nagi fetch
./nagi build
./nagi test
./nagi fmt
./nagi lint
```

`build`, `test`, and `lint` cover the host-compatible workspace and exclude
`nagi-kernel`; they do not replace a Nagi target build. Use the milestone's
documented target and acceptance workflow for target changes. The supported
top-level image and QEMU commands are `./nagi image`, `./nagi run`, and the
milestone commands shown by `./nagi --help`.

Report exact commands, relevant outputs, commit or source revision, host and
toolchain, and whether QEMU/acceptance ran. Separate verified results from
unverified work and blockers. Never delete a failing test or weaken an
assertion merely to obtain a pass. Check the final repository state and run
`git diff --check` after editing.

`./nagi clean` removes repository-owned `target/` and `out/` output trees.
Preserve any logs, disk images, or package artifacts needed for review before
running it. See [`docs/developer-preview/README.md`](docs/developer-preview/README.md)
for the current developer-host and diagnostic workflow.

## Documentation and dependency notices

Keep durable implementation evidence with the owning workstream and update
the milestone status after meaningful implementation changes. Keep the owning
workstream in sync, and avoid rewriting unrelated history. Do not duplicate a
milestone table in a way that can become stale. For new or changed
dependencies, update the source lock, patch/provenance records, and
[`THIRD_PARTY_NOTICES.md`](THIRD_PARTY_NOTICES.md) as required by the repo
rules. The Nagi OS license has not been selected; do not infer it from a
dependency or sample package.

## Security reports

Do not place credentials, private keys, tokens, personal data, document
contents, or other sensitive material in public issues, pull requests, or
logs. See [`SECURITY.md`](SECURITY.md) for the current reporting boundary.
