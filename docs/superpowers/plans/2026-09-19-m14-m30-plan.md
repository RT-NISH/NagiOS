# Nagi OS M14-M30 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement Nagi OS 0.1 Developer Preview milestones M14 through M30 in specification order, with real guest behavior, capability-preserving service boundaries, reproducible builds, and a passing acceptance test for every milestone that is marked `PASS`.

**Architecture:** Keep the kernel limited to low-level execution, memory, IPC, device transport, and authority. Implement audio, history, packages, SDK, browser, semantic search, AI, voice, and recovery as user-space services or host-side build/release tooling. Every guest acceptance path must exercise the Nagi implementation inside QEMU; host fixtures may provide deterministic test inputs but may not stand in for guest services.

**Tech Stack:** Rust workspace and pinned nightly toolchain, Nagi x86-64 target, QEMU/OVMF/q35, existing user-space VFS/network/UI/PAL layers, C ABI/SDK, Servo with an explicit `target_os = "nagi"` adapter, llama.cpp/GGUF, whisper.cpp, PowerShell and Git Bash acceptance wrappers.

## Global Constraints

- Implement milestones strictly as `M14 -> M15 -> ... -> M30`.
- Mark a milestone `PASS` only after build, focused tests, QEMU boot where applicable, acceptance test, log review, and status update.
- Nagi is an independent OS; Windows/Linux/macOS are development hosts only.
- Do not add Linux/POSIX high-level behavior to the production kernel.
- Do not use host filesystems, sockets, audio, rendering, AI, or process execution as guest implementations.
- Preserve capability checks and rights attenuation; AI never receives arbitrary OS authority.
- Servo is the only planned browser engine; do not substitute Chromium, WebKit, NetSurf, X11, or Wayland.
- Use pinned third-party revisions and Nagi-owned patch/adaptor files.
- English is canonical for internal identifiers and diagnostics; `en-US` and `ja-JP` are equal first-class user locales; internal text is UTF-8.
- Use real test inputs and deterministic validation. Test doubles are allowed only for explicitly orchestration-only tests.
- For each new behavior, write a failing focused test first, verify the expected failure, implement the minimum behavior, and re-run the test before refactoring.
- Preserve the existing M0-M13 acceptance tests and run regression gates after each milestone.

- [ ] Logs reviewed for expected ordered markers and absence of hidden host escape.
- [ ] `git diff --check` passes.
- [ ] `docs/implementation_status.md` records exact evidence, blockers, and next action.
